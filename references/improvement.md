# 有效迭代与反馈筛选

用户已授权在使用本skill处理科研阅读、学习、实验辅助和汇报任务时，持续提炼可复用改进。实际操作中发现或收到关键问题时，及时修复当前产物，并在同次任务中将有证据、可复用的教训更新到相应规则；无需等任务结束或错误重复。仅因既有规则执行遗漏而出现的问题，先落实原规则，只有修正触发或检查位置能够防再犯时才更新。轻量复盘不要求用户填写表格，不变成额外交付；不等于每次修改文件，也不自动启动后台任务。

## 一、先辨认新问题

判断本次相较既有流程出现了什么新问题，依据是用户反馈、可核实的错误、实际交付缺陷，还是助手自己的偏好。记录其原因与有效修复，不只重复“内容要充实”等笼统要求。若旧规则已经覆盖，只是执行遗漏，应落实旧规则；只有发现检查位置、触发条件或适用范围确实缺失时才调整流程。

## 二、分流而非全部保留

| 类别 | 例子与判断 | 处理 |
|---|---|---|
| 本次临时约束 | 本篇论文、截止日期、指定页数、一次性配色、临时保留某张图 | 仅用于当前任务；结束后不写入skill或长期反馈记录。无需删除用户文件或聊天 |
| 论文/项目特有知识 | 本文缩写含义、故障假设、数据参数、尚待解决的问题 | 保留在已有任务材料中；需要跨任务保存时按用户要求维护项目记录，不升级为通用规则 |
| 可复用流程改进 | 讲稿依赖未展示的对象、将上界误称最低值、实验结果缺基线条件 | 抽象成有适用范围的检查，优先修改相应阅读/汇报参考文件 |
| 明确长期偏好 | 用户明确要求以后沿用，且不违反当前要求优先原则 | 写入preferences.md，注明适用场景；未被否定的做法不等于已获认可 |
| 尚不确定的候选经验 | 只有一个模糊反馈，无法判断原因或修复效果 | 不改变默认行为；只在确有未来复核价值时简记候选及待验证条件，否则不保存 |

## 三、写入前检查价值与边界

每条候选改进需要回答：
- 换一篇论文、另一个课题或另一种汇报，这条规则仍有用吗？只对当前材料成立的内容不进入全局。
- 它修复的具体失误是什么，如何判断改善，证据是否充分？一次清楚、可核实的通用错误即可修复，不要求机械等待多次复发。
- 哪些模式适用，哪些情况不适用？优先写进模式参考文件，只有跨模式要求才进入SKILL.md。
- 是否与已有规则重复或冲突？合并、收窄或替换，避免叠加越来越多限制。
- 是否会让简单答疑变成全文分析、让文献阅读触发PPT、让特定示例成为固定模板？若会，应修正或不采纳。

没有足够复用价值时，明确选择不更新。有效迭代以减少反复错误和提高结果质量为目的，不以新增规则条数衡量。

## 四、更新与维护

- 直接修改现有literature-research-assistant目录，不新建skill或备份；遵守实际目录写入权限，不扩大外部操作授权。
- 对实际采纳的更新，在feedback-log.md简记日期、问题原因、规则改动、适用范围与依据。不保存整段对话、敏感研究细节或无用临时要求。
- 少量候选记录应标明未生效；后续遇到相关任务时复核，证据支持则采纳，否定或被取代则移除候选，不无限积累。
- 当新反馈表明旧规则不合适时，修订或撤销旧规则；删除无效规则与增加规则同样重要。保留简短可追溯说明即可，不累积冗长历史。
- 更新后运行可用skill-creator的quick_validate.py并检查引用路径；依赖缺失则如实说明校验边界，不声称全部验证完成。使用一个适用例和一个不应触发的反例检查范围，例如“解释公式”不生成PPT、“仅本次12页”不改变之后页数。
- 每次实际更新本skill后，在本次任务的交付说明中主动告知：发现了什么问题、具体修改了哪些能力或规则、更新前后实际行为有什么区别；涉及重要限制、未完成项或未做验证时如实说清。只报告真实落盘的更改，必要时链接相关文件，不以“已优化”代替具体内容。更新过程中继续完成用户任务，不为说明而中断；没有实际更新时不伪称改过，也无需例行复盘。
- 此机制在本skill被使用的任务中执行，不承诺监视所有聊天、后台自动学习或不经检查永久记忆。
